The audit found 13 defects: 2 Blocker, 8 Major, and 3 Minor. Nine runtime defects were reproduced through public APIs, including a use-after-free confirmed by Miri. All probes are under `tmp/probe/`; I did not edit `crate/`.

## Blocker

### 1. Clearing expiration leaves a dangling timer pointer

Location: `crate/src/common/timer_wheel.rs:493`

When a queued timer’s expiration becomes `None`, the iterator drops its node without clearing the cache entry’s pointer to it. Later maintenance dereferences freed memory. Both cache implementations use this timer wheel.

Evidence: `timer_clear` creates a two-second expiration, waits 1.2 seconds, and reads with an expiry callback returning `None`. Subsequent maintenance panicked natively. Miri with Tree Borrows reported a dangling reference/use-after-free in `TimerWheel::unlink_timer`.

Fix: clear the entry’s timer pointer before dropping a node whose expiration is unset, and return a descheduling event.

### 2. Fallible initialization can panic an unrelated infallible caller

Locations: `crate/src/sync/value_initializer.rs:348`, `crate/src/future/value_initializer.rs:592`

`get_with` identifies its waiters using `TypeId::of::<()>()`. This collides with `try_get_with` when its error type is `()`. A waiting `get_with` can receive the other operation’s error and execute `unreachable!()`.

Evidence: `unit_error_collision` and `future_collision` start `try_get_with` first, then a concurrent `get_with` for the same key. Returning `Err(())` from the first initializer caused the second caller to panic in both implementations.

Fix: use a private marker type to distinguish infallible initialization from every caller-supplied error type.

## Major

### 3. Concurrent invalidation can resurrect invalidated entries

Locations: `crate/src/sync/base_cache.rs:971`, `crate/src/future/base_cache.rs:1115`

Concurrent `invalidate_all` calls can store their timestamps out of order. An older timestamp overwrites a newer one, making entries valid again despite a completed invalidation.

Evidence: `invalidate_all_race` runs concurrent invalidators while another thread repeatedly inserts, invalidates, and reads one key. Invalidated values reappeared in all four runs, within 212 iterations.

Fix: advance the invalidation timestamp monotonically with a compare-and-exchange loop, handling the unset sentinel separately.

### 4. Asynchronous computations release their lock before writing

Locations: `crate/src/future/value_initializer.rs:350`, `crate/src/future/value_initializer.rs:488`

Calling `set_waiter_value` consumes the guard, removes the waiter, and releases its lock before applying the computed operation. Another computation can therefore read the same old value and overwrite an update, violating the documented serialization guarantee.

Evidence: the main probe pauses one `and_upsert_with` write inside the weigher. A second increment completes while it is paused. Starting from zero, the final counter is one instead of two.

Fix: retain the waiter guard until the computed insert or removal has completed.

### 5. Reordered operation logs leave permanently occupied capacity

Locations: `crate/src/sync/base_cache.rs:1469`, `crate/src/future/base_cache.rs:1620`

An insertion can publish its map entry before queuing its operation log. If removal and its maintenance finish first, processing the delayed insertion log admits an entry already removed from the map.

Evidence: `reordered_remove` pauses insertion in `expire_after_create`, removes the entry, processes maintenance, then resumes insertion. The empty cache subsequently reports one entry. Further maintenance and `invalidate_all` do not repair it; a capacity-one cache rejects a new key.

Fix: reject an upsert superseded by an already-applied removal generation instead of admitting its obsolete metadata.

### 6. Failed replacement attempts corrupt weight accounting

Locations: `crate/src/sync/base_cache.rs:525`, `crate/src/sync/base_cache.rs:650`; corresponding code at `crate/src/future/base_cache.rs:525` and `:780`

Optimistic replacement attempts mutate shared `EntryInfo` before their map compare-and-exchange succeeds. After an unsuccessful attempt, the retry can read its own speculative weight as the previous weight, producing an incorrect accounting delta.

Evidence: `weight_race` controls two replacements by pausing a valid `Clone` implementation. After maintenance, entries weighing 13 collectively report weight 12. Removing the updated entry leaves a weight-ten entry while reporting nine.

Fix: derive accounting from immutable, committed versions, or serialize same-key metadata changes with their map updates.

### 7. Generation wraparound prevents automatic eviction

Location: `crate/src/common/concurrent/entry_info.rs:97`

The ordinary comparison `current >= value` rejects every wrapped generation after `policy_gen` reaches 65,535. Entries then remain dirty and are skipped by expiration and capacity eviction.

Evidence: `generation` performs maintenance after each write. With an initial insertion plus 65,535 replacements, expiration makes `get` return `None`, but repeated maintenance retains entry count and weight at one. The neighboring case with 65,534 replacements removes the entry correctly.

Fix: compare generations using wrapping-distance ordering rather than ordinary integer ordering.

### 8. Returning `None` fails to clear an elapsed expiration

Locations: `crate/src/sync/base_cache.rs:689`, `crate/src/future/base_cache.rs:819`

An elapsed deadline becomes `current_duration = None`. If `expire_after_update` returns `None` to clear expiration, the equality check skips the update, preserving the expired deadline.

Evidence: `refresh_expired` uses a 20-millisecond expiration, waits 40 milliseconds, then refreshes through `get_with`. The update callback explicitly returns `None`. `get_with` returns the new value, but an immediate `get` returns `None`.

Fix: distinguish an elapsed deadline from an absent deadline, and clear the stored expiration when requested.

### 9. Removal notifications ignore per-entry expiration

Locations: `crate/src/sync/base_cache.rs:2316`, `crate/src/sync/base_cache.rs:2340`; corresponding functions at `crate/src/future/base_cache.rs:2513` and `:2554`

Notification classification checks global TTL and idle expiration but omits per-entry deadlines. Consequently, already-expired entries receive `Explicit` or `Replaced` notifications instead of `Expired`.

Evidence: `notification_cause` inserts entries with 20-millisecond per-entry expiration, waits 40 milliseconds, then removes one and replaces another. The listener receives `Explicit` and `Replaced`.

Fix: preserve and check the old per-entry deadline alongside the timestamps used to classify removal.

### 10. Rustdoc fails with warnings denied

Locations: `crate/src/sync/entry_selector.rs:201`, `crate/src/sync/entry_selector.rs:743`, `crate/src/common/concurrent/arc.rs:83`, `crate/src/common/concurrent/arc.rs:99`

Two example links refer to an undefined link label, `ptr::eq` is unresolved, and a bare URL triggers a warning.

Evidence: both verification gates failed the rustdoc step with these four diagnostics.

Fix: correct the example references, fully qualify `std::ptr::eq`, and format the URL as a hyperlink.

## Minor

### 11. Unsafe operations lack local safety justifications

Examples: `crate/src/cht/map/bucket.rs:37`, `crate/src/common/concurrent/arc.rs:115`, `crate/src/common/concurrent/arc.rs:145`

The advisory pass reports 77 unsafe-block and 13 unsafe-implementation safety-comment diagnostics. Confirmed examples omit the allocation, lifetime, and ownership arguments needed to review raw initialization and destruction.

Fix: document the relevant invariants at each unsafe operation and implementation.

### 12. Public documentation is incomplete

Examples: `crate/src/future/entry_selector.rs:242`, `crate/src/sync/segment.rs:279`, `crate/src/notification.rs:44`

The advisory pass identifies 23 undocumented public items and 20 APIs without canonical `# Errors` sections. Fourteen undocumented items belong to the optional debug-counter API.

Fix: document the exposed behavior and error conditions.

### 13. Eight public types lack `Debug`

Examples: `crate/src/future/builder.rs:58`, `crate/src/sync/entry_selector.rs:22`, `crate/src/common/iter.rs:22`

The advisory pass confirms eight public types without `Debug`, preventing their use in ordinary diagnostic formatting.

Fix: provide implementations that omit callback internals where necessary.
