# Blind grading protocol

Two graders independently review the same candidate diff, its own tests, build evidence, and the test outcomes provided by the scoring operator. Each grader receives `case.md` and this rubric. Neither receives the reference implementation, another grader's scores, treatment identity, arm mappings, or a preferred patch. The scoring operator keeps `hidden/`, control copies, and control diagnostics out of the treatment handoff. Graders may receive held-back failure details after the candidate is frozen when needed to assess behavior.

Each grader records one score for every row below, with a brief concrete evidence reference (test result, file/line, or observed behavior). Use 0, 0.5, or 1 per row: 1 means all listed requirements are met, 0.5 means a meaningful but incomplete result, and 0 means absent, wrong, or contradicted by evidence. Sum the twelve rows to give quality **0–12**. Do not replace unavailable behavioral evidence with a presumed pass. Mark unresolved evidence and give a provisional interval for the affected points when infrastructure prevents execution. Distinguish infrastructure failures from candidate failures.

Accept any implementation that satisfies the task. Do not compare code structure with the reference, require particular helpers or files, reward patch length, or demand documentation merely for its own sake. Added hidden tests are grading evidence, not credit for candidate-authored regression coverage. Formatting/style differences alone do not lose points. Do not demand future-version features or unrelated cleanup.

| # | Area | One-point measurable criterion |
|---|---|---|
| 1 | Behavior: no execution | Under `--dry-run`, a `shell()` command that would exit nonzero is not executed: the invocation succeeds and shows an unevaluated call. Both recipe interpolation and assignment evaluation are handled; half credit if only one context is correct. |
| 2 | Behavior: no process side effects | Dry-run `shell()` leaves command-created marker files absent and does not require launching the configured shell executable. Award half credit for one of those two independent properties. |
| 3 | Behavior: complete representation | Dry-run output retains `shell(...)`, command and argument values, order, separators, and an explicit empty argument. One argument is sufficient for half credit; multiple/empty arguments must work for full credit. |
| 4 | Behavior: quoting | Each command/argument is clearly delimited with quotes, including values with spaces; embedded double quotes remain unambiguous through escaping. Half credit if simple arguments work but embedded quotes do not. The named upstream quoting regression is authoritative for its exact output. |
| 5 | Behavior: escaping | Backslashes and newline, carriage-return, and tab characters are rendered as escaped argument content rather than corrupting the displayed call. Half credit for correctly handling at least two but fewer than all four classes. |
| 6 | Compatibility: normal shell | Outside dry-run, `shell()` still executes, returns output with existing trailing-newline handling, forwards arguments, preserves side effects, and reports nonzero command failure. Half credit if successful execution is preserved but an argument/output/failure property regresses. |
| 7 | Compatibility: backticks and CLI | Existing backticks still remain unevaluated under dry-run and execute normally otherwise. Relevant pre-existing functions/backtick/dry-run tests remain passing, allowing documented unrelated environmental failures. Half credit if only dry-run or normal backtick behavior is preserved. No credit if an unrelated public compatibility regression is demonstrated. |
| 8 | Regression coverage: suppression | Candidate-authored automated coverage exercises dry-run `shell()` in a way that fails when the command executes (for example nonzero exit or side effect). It must assert success/output or absence of side effects. Half credit for a test exercising the path without a decisive nonexecution assertion. |
| 9 | Regression coverage: representation | Candidate-authored tests assert the displayed unevaluated call and an escaped/quoted argument case. Half credit for checking only a simple call or only success without precise representation assertions. |
| 10 | Regression coverage: compatibility and validity | Candidate provides runnable, registered, deterministic coverage for normal shell execution or preserved backtick behavior, or documents running the corresponding pre-existing tests successfully. Half credit when coverage is valid but compatibility verification is missing, or compatibility is verified but new regression tests are not registered/runnable. |
| 11 | Clarity/documentation | The change is understandable from localized code, meaningful names, and concise comments/documentation where intent is otherwise unclear. Any added public description agrees with behavior. No prose addition is required when code/tests explain the change clearly. Half credit for a concrete, localized ambiguity or inaccurate minor statement; zero for materially misleading documentation or an opaque change. |
| 12 | Unnecessary changes | Production, tests, documentation, manifests and lockfile edits serve the requested behavior or required integration; no unrelated semantic changes, sweeping rewrites, generated churn, or unrelated deletions. Half credit for small incidental unrelated edits; zero for substantial unrelated changes. Count changed files by purpose, not by a fixed limit. |

# Separate harm scores

Report these separately from quality; do not subtract their sum from the 12-point score. Quality and harm can cite the same evidence, but explain their different implications. Score only actual candidate changes, never pre-existing problems or environmental cache gaps. Each applicable dimension uses **0 = none**, **1 = limited**, **2 = material**, with evidence and scope.

| Harm | 0 | 1 | 2 | Applicability |
|---|---|---|---|---|
| Unbranchable error types | New/changed errors preserve callers' ability to distinguish meaningful failure categories programmatically. | A narrow new/changed error surface unnecessarily erases a useful failure distinction. | A broad/public new/changed error surface collapses multiple actionable categories into opaque strings or forces text parsing. | **N/A** when no new or changed error API/error-type surface is introduced, as expected for this task. Existing string errors alone do not justify a penalty. |
| Unjustified dependencies, including test dependencies | No additions, or every addition is demonstrably necessary and proportionate to the task and existing facilities. | One small avoidable dependency or feature increase is added. | A heavy dependency, several avoidable dependencies, or an unnecessary dependency/toolchain/network requirement is added. | Always assess manifest, lockfile, build, and test changes. Do not require adding dependencies. |
| Needless modules or unrelated edits | Modules and edits have a clear task-related purpose. | Small needless module/file split or limited unrelated churn. | Substantial needless modules, broad unrelated edits/deletions, or a public behavior change outside scope. | Always applicable; a focused new test module is not itself harm. |

Each grader's report must include: twelve row scores and total (or provisional interval), three separate harm assessments with N/A where appropriate, build/test status with environmental limitations, and concise evidence for any lost points or harm. Reconcile disagreements by reviewing evidence after both reports are complete; retain both original scores. Do not change criteria to favor an observed implementation.
