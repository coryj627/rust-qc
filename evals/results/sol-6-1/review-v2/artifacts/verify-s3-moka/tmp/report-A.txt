P0003 Async compute operations release their lock before committing the result


P0004 [src/future/value_initializer.rs:350](/work/crate/src/future/value_initializer.rs:350).


P0005 Expected: Concurrent `and_upsert_with` calls execute serially, as documented in `src/future/entry_selector.rs:335`.


P0006 Observed: `set_waiter_value` consumes the guard and releases the per-key lock before the subsequent insert or removal. Another computation can therefore read the previous value before the first computation commits.


P0007 Evidence: An executed, deterministic single-thread test used an async eviction listener to pause writes. Two upserts both read `10` and left `11`; serialized execution should read `10`, then `11`, and leave `12`. A separate four-worker test also lost increments.

P0010 Mixing infallible and unit-error loaders can panic


P0011 Locations: [src/sync/value_initializer.rs:348](/work/crate/src/sync/value_initializer.rs:348), [src/future/value_initializer.rs:592](/work/crate/src/future/value_initializer.rs:592).


P0012 Expected: `get_with` remains infallible when another caller concurrently uses `try_get_with` on the same key.


P0013 Observed: Both `get_with` and `try_get_with::<_, ()>` use `TypeId::of::<()>()` to identify their waiters. If the fallible loader returns `Err(())`, the infallible loader receives that error and reaches `unreachable!()`.


P0014 Evidence: Executed sync and async tests both panicked at `src/sync/cache.rs:1053` and `src/future/cache.rs:1597`. A control using a different error type passed.


P0015 Consequence: An ordinary loader error can panic another caller whose initializer cannot fail.

P0017 Medium


P0018 Returning `None` does not clear an already-expired deadline


P0019 Locations: [src/sync/base_cache.rs:689](/work/crate/src/sync/base_cache.rs:689), [src/future/base_cache.rs:819](/work/crate/src/future/base_cache.rs:819).


P0020 Expected: `Expiry::expire_after_update` returning `None` clears expiration, as documented in `src/policy.rs`.


P0021 Observed: An elapsed deadline becomes `current_duration = None` because `checked_duration_since` fails. When the callback also returns `None`, the equality check skips clearing the stored deadline.


P0022 Evidence: Executed tests inserted an immediately expired value, then replaced it with a value whose expiry callback returned `None`. Both cache variants returned `None` from the next `get`, instead of the replacement. Clearing an unexpired deadline passed its control test.


P0023 Consequence: A successful replacement can remain immediately expired and unavailable.


P0024 Distinguish an elapsed deadline from an absent deadline, and ensure a callback returning `None` clears the stored timestamp.


P0025 Removal returns values that have already been invalidated


P0026 Cancelling get_with leaves a Computing waiter that blocks later initialization. src/future/value_initializer.rs:239. future::Cache::get_with installs a per-key Computing waiter before awaiting the user initializer, but removes it only when that initializer completes. Polling a get_with whose initializer is pending and then dropping the enclosing future leaves that waiter registered. A later get_with for the same absent key waits on the abandoned computation instead of polling its own initializer, so an ordinary cancelled cache fill prevents a subsequent request from completing.


P0027 Locations: [src/sync/cache.rs:1619](/work/crate/src/sync/cache.rs:1619), [src/future/cache.rs:1964](/work/crate/src/future/cache.rs:1964).


P0028 Expected: Retrieval respects logical invalidation. The compute API also documents `Op::Remove` on an absent entry as returning `StillNone`.


P0029 Observed: Removal clones the physical hash-table value without applying the validity checks used by reads.


P0030 Evidence: Executed sync and async tests inserted `42`, called `invalidate_all`, and confirmed `get` returned `None`. Nevertheless, `remove` returned `Some(42)`. In separate compute tests, the closure received `None`, but returning `Op::Remove` produced `Removed(42)` instead of `StillNone`.


P0031 Consequence: Callers can receive invalidated data and contradictory compute results before maintenance removes the underlying entry.


P0032 Check logical validity when determining the returned value, while still performing physical removal and maintenance bookkeeping.


P0033 Generation wrap prevents maintenance from cleaning up hot entries


P0034 [src/common/concurrent/entry_info.rs:97](/work/crate/src/common/concurrent/entry_info.rs:97).


P0035 Expected: The wrapping generation counters continue to distinguish pending updates from fully processed entries.


P0036 Observed: `current >= value` rejects the transition from policy generation `65535` to `0`. Consequently, the entry remains marked dirty after its write operations have been processed.


P0037 Evidence: Executed sync and async tests performed 65,535, 65,536, and 65,537 writes to one key, then invalidated everything and ran maintenance three times. Remaining entry counts were respectively `0`, `1`, and `1`.


P0038 Consequence: Frequently updated entries retain invalidated values and consume capacity after maintenance. Source inspection also shows dirty entries being skipped during eviction.


P0039 Compare generations using wrapping sequence-number ordering, without the ordinary numeric-order rejection. Add wrap-boundary tests.
