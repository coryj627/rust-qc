P0074 Async compute operations can lose updates.  
   [src/future/value_initializer.rs:350](/work/crate/src/future/value_initializer.rs:350).


P0075    `and_compute_with` promises to serialize operations on the same key. However, `set_waiter_value` consumes the guard and releases the key’s compute lock before the requested insertion or removal finishes.


P0076    **Executed evidence:** `future_compute_keeps_lock_until_write_finishes` pauses an async eviction listener while three compute operations increment the same counter. Expected results are `1, 2, 3`, leaving `3` cached. Actual results are `1, 2, 2`, leaving `2`. Callers implementing counters or other read-modify-write operations can lose changes. Existing compute tests delay the computation itself but do not exercise this subsequent write suspension.


P0077 A normal borrowed-entry cache hit produces an entry whose `key()` panics.  
   [src/sync/cache.rs:1422](/work/crate/src/sync/cache.rs:1422).


P0078    `get_or_try_insert_with_hash_by_ref_and_fun` passes `false` to `get_with_hash`, ignoring its `need_key` argument. Consequently, `entry_by_ref(...).or_try_insert_with(...)` returns an existing value without its key.


P0079    **Executed evidence:** Both `sync_borrowed_try_entry_hit_has_key` and `segmented_borrowed_try_entry_hit_has_key` insert `"key" → 42`, retrieve the existing entry, verify its value, and then panic at [src/common/entry.rs:59](/work/crate/src/common/entry.rs:59): `Bug: Key is None`. Expected behavior is to return `"key"`. Formatting the entry with `Debug` also calls `key()` and can panic, based on source inspection. The equivalent future-cache test passes.


P0080 Reordered weighted updates corrupt capacity accounting and prevent valid admissions.  
   Locations: [src/sync/base_cache.rs:1460](/work/crate/src/sync/base_cache.rs:1460), [src/future/base_cache.rs:1611](/work/crate/src/future/base_cache.rs:1611).


P0081    Concurrent updates can enqueue their maintenance records in a different order from their changes to the hash table. Applying each record’s old/new weight delta with saturating subtraction loses accounting information when subtraction underflows.


P0082    **Executed evidence:** The sync and future `out_of_order_weight_updates` tests start with weight `1`, pause the update to `2` inside its expiry callback, and complete the update to `3` first. After both writers finish and maintenance runs, the sole cached value is `3`, but `weighted_size()` is `4`.


P0083    A further synchronous test with capacity `3` observes the fitting value being evicted, leaving an empty cache reporting weight `1`. Inserting another weight-`3` value is then rejected. This creates persistent unnecessary cache misses after concurrent activity has ended.


P0084 Returning `None` from an update-expiry callback fails to clear an elapsed deadline.  
   Locations: [src/sync/base_cache.rs:696](/work/crate/src/sync/base_cache.rs:696), [src/future/base_cache.rs:826](/work/crate/src/future/base_cache.rs:826).


P0085    The `Expiry::expire_after_update` documentation says returning `None` clears expiration. For an elapsed deadline, `checked_duration_since` yields `None`; the equality optimization then treats the callback’s returned `None` as unchanged and retains the expired timestamp.


P0086 Failed and_try_compute_with removes the existing cached value. src/sync/value_initializer.rs:241. For an occupied key, sync::Cache::entry(key).and_try_compute_with passes the current Entry by value to the callback before checking its Result. Consuming that Entry removes the existing mapping, so if the callback returns Err the previous value is lost even though no Put or Remove operation was requested. For example, rejecting an attempted update of a cached counter from 7 leaves the key absent instead of preserving 7.


P0087    **Executed evidence:** Both `clear_elapsed_expiry_on_update` tests create an entry with a 10 ms lifetime, wait 30 ms, then replace it. The update callback is confirmed to execute and returns `None`. Expected: `get` returns the replacement value `2`. Actual: `get` returns `None`. An ordinary refresh can therefore complete successfully while leaving its replacement unreadable.


P0088 Generation-counter wrap prevents subsequent policy eviction.  
   [src/common/concurrent/entry_info.rs:97](/work/crate/src/common/concurrent/entry_info.rs:97).


P0089 Cache iterator yields expired entries that maintenance has not removed. src/common/iter.rs:117. sync::Cache iteration enumerates keys still present in the backing hash table and yields their cached values without rechecking expiration. If a value reaches its configured time-to-live while its physical entry remains pending maintenance, iter().next() can return that expired value. This affects both a newly created iterator and one created before expiration, allowing iteration-based exports to include values that should already have expired.


P0090    Entry generations deliberately wrap as `u16`, but `current >= value` prevents the policy generation from following the wrap from `65535` to `0`. The entry remains marked dirty, so maintenance skips it.


P0091    **Executed evidence:** Both `lru_after_generation_wrap` tests perform 65,536 writes to one key in a capacity-one LRU cache, running maintenance after every write. After inserting another key and running maintenance, the older key still returns `Some(65535)` instead of being evicted. A frequently updated entry can become persistently ineligible for policy eviction once writes stop. No concurrent scheduling is needed.
