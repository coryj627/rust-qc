P0100 Found **seven correctness issues and one documentation issue**. The existing test suite passes, but targeted regressions reproduce the correctness failures.


P0101 Concurrent async entry updates lose writes.  
   [src/future/value_initializer.rs:350](/work/crate/src/future/value_initializer.rs:350) releases the waiter guard before applying the computed operation.


P0102    The documented contract serializes same-key `and_upsert_with` and compute calls. With an async eviction listener that yields, later calls can read the same value while preceding writes wait for the key lock. **Ten concurrent increments produce `2` instead of `10`.** This makes concurrent counters and read-modify-write updates incorrect.


P0103    Executed evidence: [review_async_compute.rs](/work/tmp/review/tests/review_async_compute.rs). Source inspection identifies the premature guard release as the cause.


P0104 A cached borrowed-key entry can panic when its key is accessed.  
   [src/sync/cache.rs:1422](/work/crate/src/sync/cache.rs:1422) passes `false` instead of `need_key` when reading an existing entry.


P0105    `entry_by_ref(...).or_try_insert_with(...)` should return an `Entry` containing both key and value. On a cache hit, the synchronous implementation omits the key. Calling `entry.key()` panics with **`Bug: Key is None`**; formatting the entry through `Debug` also calls `key()`.


P0106    Executed evidence: [review_entry_key.rs](/work/tmp/review/tests/review_entry_key.rs). The sync test fails; the equivalent async control passes. The existing doctest checks the key after insertion but omits that assertion on its cache-hit path.


P0107 Mixing fallible and infallible initialization can cause an internal panic.  
   [src/sync/value_initializer.rs:348](/work/crate/src/sync/value_initializer.rs:348), [src/future/value_initializer.rs:592](/work/crate/src/future/value_initializer.rs:592).


P0108    `get_with` uses `TypeId::of::<()>()` to identify its initializer state. `try_get_with::<_, ()>` uses the same identifier. If a concurrent fallible initializer returns `Err(())`, the infallible caller receives that error and reaches `unreachable!()` at [sync/cache.rs:1053](/work/crate/src/sync/cache.rs:1053) or [future/cache.rs:1597](/work/crate/src/future/cache.rs:1597).


P0109    Ordinary callers using the valid unit error type can therefore panic without either initializer panicking. Executed evidence: both tests in [review_initializer_types.rs](/work/tmp/review/tests/review_initializer_types.rs) fail with the internal panic.


P0110 Removal returns values that are already logically absent.  
   [src/sync/cache.rs:1619](/work/crate/src/sync/cache.rs:1619), [src/future/cache.rs:1964](/work/crate/src/future/cache.rs:1964).


P0111    Removal clones the physical map value without applying expiration or invalidation checks. After `invalidate_all()`, `get` returns `None`, but `remove` returns **`Some(old_value)`**. This also affects `SegmentedCache`.


P0112    The entry-compute contract is contradicted directly: after TTL expiration, its callback receives `None`, requests `Op::Remove`, and receives **`CompResult::Removed(old_value)` instead of `StillNone`**. Callers can consequently consume invalidated values or misinterpret compute results.


P0113    Executed evidence: public tests in [review_public_api.rs](/work/tmp/review/tests/review_public_api.rs), plus deterministic expiration tests appended to both scratch cache modules.


P0114 Returning `None` from an expiry update can leave the replacement expired.  
   [src/sync/base_cache.rs:689](/work/crate/src/sync/base_cache.rs:689), [src/future/base_cache.rs:819](/work/crate/src/future/base_cache.rs:819).


P0115    `Expiry::expire_after_update` documents that `None` clears expiration. For an elapsed deadline, `checked_duration_since` produces `None`; when the callback also returns `None`, the equality optimization skips clearing the stored deadline.


P0116    Both caches then return **`None` after inserting a replacement that should have no expiration**. Successful writes can effectively disappear until the expired physical entry is removed.


P0117    Executed evidence: deterministic mocked-clock tests and public zero-duration boundary tests in [review_public_api.rs](/work/tmp/review/tests/review_public_api.rs).


P0118 Generation-counter wraparound breaks eviction of frequently updated keys.  
   [src/common/concurrent/entry_info.rs:97](/work/crate/src/common/concurrent/entry_info.rs:97).


P0119    Entry generations explicitly wrap, but `current >= value` prevents the policy generation from advancing from `65535` to `0`. The policy generation freezes, leaving subsequent versions marked dirty even after their writes have been processed.


P0120    In both cache variants, after 65,535 replacements of one key, a capacity-two LRU cache retains that oldest key when two newer keys are inserted. The expected oldest entry remains **`Some(65535)`**, so newer entries lose capacity to it.


P0121    Executed evidence: `review_lru_after_generation_wrap` tests appended to both scratch cache modules, with maintenance run after every write.


P0122 Conditional replacements report incorrect entry metadata.  
   [src/sync/cache.rs:1050](/work/crate/src/sync/cache.rs:1050), [src/future/cache.rs:1594](/work/crate/src/future/cache.rs:1594).


P0123    `or_insert_with_if` successfully replaces an existing value but constructs the resulting entry with `is_old_value_replaced = false`. That contradicts [Entry’s documented contract](/work/crate/src/common/entry.rs:84).


P0124    Callers using this flag to distinguish insertion from replacement receive the wrong result. Executed evidence: both tests in [review_replacement_flag.rs](/work/tmp/review/tests/review_replacement_flag.rs) confirm the value changed from `10` to `20`, then fail because the replacement flag is false.
