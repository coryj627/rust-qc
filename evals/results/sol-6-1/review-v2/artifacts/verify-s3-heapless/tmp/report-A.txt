P0003 Concurrent SPSC peeking lacks synchronization

P0004 `src/spsc.rs:268`, `src/spsc.rs:823`.

P0005 Expected: a consumer may safely inspect an item published by its producer. Observed: `peek` checks availability with relaxed loads, then references the item without acquiring the producer’s release store.

P0006 Evidence: a safe two-thread enqueue/peek test passed natively but failed under Miri with a data race at `src/spsc.rs:273`. Ordinary callers using `Consumer::peek` across threads therefore lack the synchronization needed to read the item.

P0007 acquire the published tail before accessing its element. Add a concurrent peek regression test.

P0008 Making a full deque contiguous can corrupt its state

P0009 `src/deque.rs:489`.

P0010 Expected: `make_contiguous` preserves contents and permits subsequent queue operations. Observed: one rotation branch sets `back = capacity`, violating the ring-index invariant.

P0011 Evidence: with capacity 2, push `0,1`, pop `0`, push `2`, call `make_contiguous`, then pop `1,2`. The deque incorrectly reports length 2 and exposes `[1,2]` again. A broader ordinary-operation test also aborted in `push_back` at an unchecked-index precondition.

P0012 normalize `back` when the contiguous contents fill the buffer. Test draining and refilling after full-buffer rotations.

P0013 Popping a modified sorted-list entry removes it twice

P0014 `src/sorted_linked_list.rs:713`, `src/sorted_linked_list.rs:760`.

P0015 Expected: modifying a `find_mut` guard and then calling `pop` removes that entry once. Observed: `pop` leaves `maybe_changed` armed, so the guard’s destructor removes another entry and reinserts the removed value.

P0016 Evidence: starting with `[3,2,1]`, change the middle value to `20` and pop it. The call returns `20`, but remaining iteration produces `[20,3]` instead of `[3,1]`.

P0017 disarm automatic resorting before extracting the entry. Existing tests exercise modification and popping separately.

P0018 Valid writes that fill a vector panic

P0019 `src/bytes.rs:19`.

P0020 Expected: `BufMut` accepts writes up to `remaining_mut()`. Observed: `advance_mut` rejects `pos == capacity`.

P0021 HistoryBuf::recent reports an empty buffer at exact wrap boundaries. src/history_buf.rs:429. HistoryBuf::recent_index treats write_at == 0 as the empty-buffer state without distinguishing a filled buffer whose write cursor just wrapped. For HistoryBuf<u8,4>, writing 1,2,3,4 therefore makes recent() return None instead of Some(&4), and the same loss of the latest-sample result occurs after every complete cycle. Applications reading the most recent sample receive a spurious empty result whenever the write count is a multiple of capacity.

P0022 Evidence: both `Vec::<u8,4>::new().put_slice(b"abcd")` and appending the fourth byte with `put_u8` panic with “Advance out of range”. These are safe public operations with sufficient advertised capacity.

P0023 permit equality with capacity and check the requested advance against remaining space. Add exact-capacity tests for owned vectors and views.

P0024 Panicking element destructors cause repeated drops

P0025 Locations: `src/vec/mod.rs:1527`, `src/deque.rs:237`, `src/history_buf.rs:318`.

P0026 Expected: unwinding must not run an element’s cleanup twice. Observed: these paths clear ownership metadata only after dropping elements.

P0027 Evidence: local tests used elements whose destructor increments a counter and panics once. After unwinding:

P0028 - `Vec::IntoIter` dropped every element twice, including an element already returned to the caller.
- `Deque::clear` and `HistoryBuf::clear` each dropped both elements twice.

P0029 Callers’ cleanup actions consequently run repeatedly.

P0030 relinquish ownership before invoking destructors, with guards where additional cleanup is necessary. Add panic-cleanup tests.
