## Major

### 1. Async computations release serialization before committing

Location: `src/future/value_initializer.rs:350`; also `:488`.

Expected: concurrent entry computations on one key execute serially, as documented at `src/future/entry_selector.rs:335`.

Actual: `set_waiter_value` consumes the guard and releases the computation lock before the resulting insert or removal completes. An async eviction listener can suspend that write, allowing subsequent computations to read the same previous value.

Caller impact: counters and other read-modify-write operations lose updates.

Evidence: `async_upserts_must_serialize_through_commit` performs three increments from zero while pausing the first replacement notification. The second and third computations both read `1`; the final value is **2 instead of 3**. This reproduced twice. The shared helper also serves the compute APIs.

Fix: retain the computation guard until the resulting cache operation completes, including error cleanup.

### 2. Clearing expiration fails after the deadline has elapsed

Locations: `src/sync/base_cache.rs:689`, `:696`; corresponding async code at `src/future/base_cache.rs:819`, `:826`.

Expected: returning `None` from `Expiry::expire_after_update` clears expiration, as documented at `src/policy.rs:254`.

Actual: `checked_duration_since` converts an elapsed deadline to `None`. If the callback also returns `None`, the equality check skips updating the stored expiration, leaving the elapsed deadline attached to the replacement value.

Caller impact: a successful insertion can remain immediately unavailable.

Evidence: probes insert a value with a 30 ms expiration, wait 50 ms, then replace it using an update callback that explicitly returns `None`. Both sync and async caches return **None instead of Some(2)**. A control that clears an unexpired deadline passes.

Fix: distinguish an elapsed deadline from an unset deadline—for example, retain `Some(Duration::ZERO)` for elapsed time—and ensure the callback can clear the stored expiration.

## Minor

### 3. Documentation has broken links and undocumented public APIs

Locations: `src/sync/entry_selector.rs:201`, `:743`; `src/common/concurrent/arc.rs:83`, `:99`; `src/future/entry_selector.rs:242`, `:897`.

Expected: documentation builds cleanly and explains public operations.

Actual: strict rustdoc fails on two mismatched example links, an unresolved `ptr::eq` link, and a bare URL. Advisory checks also identify **23 undocumented public items**, including both `and_try_compute_if_nobody_else` methods.

Caller impact: broken navigation and unclear behavior for public operations.

Fix: correct the links and document the exposed methods, particularly their concurrency and error semantics.

### 4. Eight public types lack Debug

Representative locations: `src/future.rs:58`, `src/future/builder.rs:58`, `src/sync/builder.rs:50`, `src/common/iter.rs:22`.

Expected: public utility types support diagnostic formatting.

Actual: both builders, both iterator types, and four entry-selector types lack `Debug`; advisory Clippy reports eight diagnostics.

Caller impact: callers cannot readily include these objects in debugging output.

Fix: provide bounded or non-exhaustive manual implementations that avoid requiring callbacks to implement `Debug`.

### 5. Unsafe operations lack local invariant explanations

Representative locations: `src/common/concurrent/arc.rs:60`, `:115`, `:144`.

Expected: unsafe operations explain their ownership, lifetime, and synchronization assumptions.

Actual: advisory Clippy reports **77 blocks and 13 implementations** without local safety comments. The examples above lack explanations for pointer validity, allocation destruction, and cross-thread use.

Impact: maintainers must reconstruct these assumptions when changing the implementation. This is a maintainability finding; no runtime defect is established by these diagnostics.

Fix: document the relevant invariants at each operation and implementation.
