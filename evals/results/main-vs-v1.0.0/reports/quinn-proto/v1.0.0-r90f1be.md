# Audit report: quinn-proto 0.11.13

## Verdict

Any client can crash a quinn-proto server, before the handshake completes, by sending a two-byte malformed transport parameter. That makes the crate unsafe to deploy as-is. Beyond that the code is mostly solid: about 1.3 million random frame and transport-parameter inputs, and differential tests of the range sets, stream reassembly and packet-number expansion, turned up nothing else. The other findings are protocol-conformance and hardening gaps found by reading.

Counts: 1 Blocker, 5 Major, 4 Minor, 2 Notes.

## Blocker

### Malformed transport parameters crash the peer that parses them
Location: src/transport_parameters.rs:472 (`max_datagram_frame_size`) and src/transport_parameters.rs:479 (`min_ack_delay`), both in `TransportParameters::read`.

Problem: both branches call `r.get().unwrap()`. The value is read from the whole remaining buffer rather than from the parameter's declared length. When that read fails, the code panics. The server reads the client's parameters from the TLS ClientHello (src/crypto/rustls.rs:129), so this needs no authentication.
- Confirmed by a probe: the inputs `20 00` and `20 01 40` panic with `called Result::unwrap() on an Err value: UnexpectedEnd` for both sides.
- A random harness hit the same line 528 times in 300,000 inputs.
- `min_ack_delay` (id 0xFF04DE1B) has the same code shape. It also has no length check and no duplicate check. My crafted probe for it used the wrong ID (…1A instead of …1B), so this branch is shown by reading only, not by a run.
- Even when the read succeeds, it ignores `len`. A parameter that declares 8 bytes but holds a 1-byte varint makes the parser read the next 7 bytes as new parameters.

Fix: decode from `r.take(len)` and require exactly `len` bytes to be consumed, as the generic `parse!` branch already does (`len != value.size()`). Return `Error::Malformed` instead of unwrapping. Add a duplicate check for `min_ack_delay`. Add `20 00` and `20 01 40` as regression tests.

## Major

### RETIRE_CONNECTION_ID accepts a sequence number that was never issued
Location: src/connection/cid_state.rs:163 (`on_cid_retirement`).

Problem: `issued` is a count, so valid sequence numbers are `0..issued`. The check `sequence > self.issued` lets `sequence == issued` through. RFC 9000 section 19.16 requires PROTOCOL_VIOLATION here. Instead the frame is accepted, `allow_more_cids` is computed, and an endpoint event goes out for a CID that doesn't exist.

Fix: use `sequence >= self.issued`, and add a unit test that retires exactly `issued`.

### Stateless reset tokens are compared in variable time
Location: src/connection/packet_crypto.rs:41 (`unprotect_header`).

Problem: `stateless_reset_token.as_deref() == Some(&packet[..])` compares plain byte slices, which bypasses the constant-time `PartialEq` that `ResetToken` provides. RFC 9000 section 10.3.1 says this comparison MUST NOT leak information about the token.

Fix: build a `ResetToken` from the last 16 bytes and compare it with `==`, or call `constant_time::eq` directly.

### Close frames can exceed the packet size budget
Location: src/frame.rs:333 (`ApplicationClose::encode`) and src/frame.rs:293 (`ConnectionClose::encode`).

Problem: the reason length is capped at `max_len - 3 - …`, which assumes a 1-byte error code. The application error code is a caller-chosen `VarInt` of up to 8 bytes. With a code of 2^30 or more and a reason longer than the space left, the frame comes out 6 bytes over `max_len`, so the close datagram is larger than the path MTU. This is derived by arithmetic: frame size = `max_len + code_size - 2`. I couldn't run the probe I wrote for it (see the closing summary).

Fix: subtract the real `error_code.size()` (and `1` for the frame type) instead of the constant `3`.

### Safe code can build a VarInt that breaks the unsafe constructor's rule
Location: src/lib.rs:280 (`impl From<StreamId> for VarInt`).

Problem: `StreamId::new(initiator, dir, index)` is public and safe and accepts any `u64` index. `From<StreamId> for VarInt` then calls `unsafe { VarInt::from_u64_unchecked(x.0) }` with no check and no SAFETY comment. An index of 2^60 or more gives a VarInt of 2^62 or more. Later, `size()` panics with "malformed VarInt" and `encode` hits `unreachable!`. This is not memory unsafety, because nothing unsafe relies on the bound. But it breaks the documented `# Safety` precondition from safe code.

Fix: check the bound in `StreamId::new` (return `Option`, or panic with a documented `# Panics` section). Alternatively, use `VarInt::from_u64(x.0).expect(...)` with a message that states why the bound holds.

### The other unsafe blocks have no SAFETY comments
Location: src/connection/send_buffer.rs:99, src/connection/send_buffer.rs:118, src/connection/mod.rs:3261.

Problem: each one calls `VarInt::from_u64_unchecked` on a stream or crypto offset. They look sound, because flow control keeps offsets below 2^62, but that reasoning isn't written down. The crate has 0 SAFETY comments in total.

Fix: replace these calls with a safe size calculation. A `const fn` that sizes a plain `u64` removes the need for `unsafe` entirely. If you keep the `unsafe`, add a `// SAFETY:` comment naming the flow-control bound.

## Minor

### The 0-RTT frame filter does not match RFC 9000
Location: src/connection/mod.rs:2756.

Problem: it rejects APPLICATION_CLOSE (type 0x1d), which RFC 9000 Table 3 allows in 0-RTT. It accepts ACK, RETIRE_CONNECTION_ID and PATH_RESPONSE, which are not allowed there and are replayable.

Fix: reject the frame types that RFC 9000 section 12.4 disallows in 0-RTT, and allow 0x1d.

### Loss detection can panic when the monotonic clock is close to its starting point
Location: src/connection/mod.rs:1674.

Problem: `now.checked_sub(loss_delay).unwrap()` panics if `Instant` is closer to its origin than `rtt * time_threshold`. That can happen shortly after boot with a large configured `initial_rtt` or `time_threshold`.

Fix: when the subtraction fails, treat no packets as lost by time, for example by matching on `Option<Instant>`.

### Clippy and rustdoc fail
Location: src/connection/assembler.rs:333, src/connection/packet_crypto.rs:91, src/crypto/rustls.rs:279.

Problem:
- Clippy 1.99 flags `derivable_impls` and `manual_filter`. These lints are newer than the toolchain the project targets, so this is toolchain drift.
- Rustdoc with default features fails on a link to `ClientConfig::with_platform_verifier`, which only exists with the `platform-verifier` feature.

Fix: apply the two clippy suggestions. Gate the doc link with `cfg_attr`, or write it as plain text.

### A public type uses a weasel-word name
Location: src/congestion.rs:100 (`ControllerFactory`).

Problem: names ending in `Factory` describe a pattern rather than what the item does. Renaming this public trait would be a breaking change.

Fix: consider a new name (for example `ControllerBuilder`) at the next breaking release.

## Closing summary

**Covered:** the baseline gate; varint and coding; the frame, packet-header and transport-parameter parsers (fuzzed); range sets, stream reassembly and packet-number expansion (differential tests); CID queue and CID state; stream receive and flow control; tokens and the bloom token log; the stateless-reset and first-packet paths in the endpoint; ACK and loss handling; RTT; NewReno and Cubic; key-phase decryption; and every `unsafe` block.

**Not checked:** BBR, MTU discovery, pacing, qlog, the stream send state machine, and connection-level scenarios with an adversarial peer.

**Why I stopped:** partway through, permission prompts for new files in `tmp/` went unanswered, so I couldn't write further probes and didn't try to get around that. As a result, the close-frame overrun and the `min_ack_delay` panic rest on reading and arithmetic rather than a run. I wrote the report once reading alone was giving diminishing returns.
