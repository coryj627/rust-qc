# quinn-proto 0.11.13 audit report

## Verdict

The test suite passes. The handshake path has one serious defect: two transport parameters sent by the peer can panic the endpoint, so an unauthenticated client can crash a server with a two-byte parameter. Findings: 1 Blocker, 5 Major, 4 Minor, 2 Notes. The other untrusted-input parsers held up under probing. Frame, packet-header and token decoding, flow control, and the CID queue showed nothing wrong, and 2 million random packet headers caused no panics.

## Blocker

### Two transport parameters panic when their length is too short
Location: `src/transport_parameters.rs:472` (max_datagram_frame_size) and `:479` (min_ack_delay).

Problem: both parameters are decoded with `r.get().unwrap()`, and the declared length is never checked first. If the declared length is 0 and the parameter is the last one, decoding the VarInt fails and the `unwrap` panics.
- Minimal panicking inputs are `[0x20, 0x00]` and `[0xc0,0,0,0,0xff,0x04,0xde,0x1b,0x00]`, for both client and server.
- An exhaustive run over 1 to 4 bytes from a 16-symbol alphabet gave 366 panics.
- This is reachable from the network. `crypto/rustls.rs:129` decodes the peer's parameters during the handshake, so a client's ClientHello can crash a server.
- The same lines have two smaller faults. The value may run past its declared length, and a repeated min_ack_delay is accepted.

Fix: decode the value the way the generic parameters at line 486 are decoded.
```rust
let value = r.get::<VarInt>()?;
if len != value.size() || params.max_datagram_frame_size.is_some() { return Err(Error::Malformed); }
```
Do the same for `min_ack_delay`, including the duplicate check. Add the two inputs above as regression tests.

## Major

### Version negotiation replies to datagrams of any size
Location: `src/endpoint.rs:164-196`.

Problem: a server answers any unsupported-version long header with a Version Negotiation packet, however small the datagram is. A 7-byte datagram with empty CIDs and version 0x1a2a3a4a got a 39-byte reply. That is a 5.6x reflection amplifier for spoofed source addresses. RFC 9000 section 5.2.2 says servers MUST drop packets with unsupported versions that are smaller than the minimum Initial size.

Fix: in the `UnsupportedVersion` arm, add `if datagram_len < MIN_INITIAL_SIZE as usize { return None; }` before encoding the reply.

### Safe `StreamId::new` can produce a VarInt above 2^62 through `unsafe`
Location: `src/lib.rs:257` (StreamId::new) and `src/lib.rs:280` (`From<StreamId> for VarInt`).

Problem: `StreamId::new` accepts any `u64` index without checking it. The conversion to VarInt then calls `VarInt::from_u64_unchecked` with no SAFETY comment. `StreamId::new(Side::Client, Dir::Bi, 1 << 61)` became a VarInt of 9223372036854775808, and encoding it panicked with "malformed VarInt". Safe code is breaking an `unsafe fn` precondition. This is not memory-unsafe today, but it does break the safety contract.

Fix: reject indexes of `MAX_STREAM_COUNT` (2^60) or more in `StreamId::new`. A `try_new` or a documented panic both work. Then use `VarInt::from_u64(x.0).expect("stream ids are < 2^62")` in the conversion.

### `HashedConnectionIdGenerator::validate` panics on short CIDs
Location: `src/cid_generator.rs:147`.

Problem: `cid.split_at(NONCE_LEN)` panics ("mid > len") on CIDs of 0 to 2 bytes. Confirmed with lengths 0 and 2. The method is public and returns `Result<(), InvalidCid>`, so callers expect an `Err`, not a panic.

Fix: `if cid.len() != self.cid_len() { return Err(InvalidCid); }` before splitting.

### Off-by-one lets the peer retire a CID that was never issued
Location: `src/connection/cid_state.rs:163`.

Problem: `issued` is the number of CIDs issued, so the valid sequence numbers are `0..issued`. The check `sequence > self.issued` accepts `sequence == issued`. RFC 9000 section 19.16 says this MUST be a PROTOCOL_VIOLATION. The practical impact is low, because the endpoint's lookup misses and nothing is removed. No test covers this path.

Fix: change the check to `sequence >= self.issued` and add a unit test for both edges.

### Three more `unsafe` blocks lack SAFETY comments
Location: `src/connection/send_buffer.rs:99`, `src/connection/send_buffer.rs:118`, `src/connection/mod.rs:3261`.

Problem: each one calls `VarInt::from_u64_unchecked` only to compute an encoded size. They appear sound, because stream offsets are capped by the peer's VarInt flow-control limits, but nothing in the code says so.

Fix: remove the `unsafe` entirely with a safe `const fn` that gives the encoded size of a `u64`, or add SAFETY comments that name the flow-control bound.

## Minor

### `drop_oversized` also drops datagrams of exactly the maximum size
Location: `src/connection/datagrams.rs:149`.

Problem: the doc says it drops datagrams "larger than `max_payload`", but `len < max_payload` also drops ones of exactly that size. `send()` accepts `len <= max`, so after black-hole detection a legal maximum-size datagram is silently lost.

Fix: change the comparison to `<=`.

### Clippy fails on this toolchain (toolchain drift)
Location: `src/connection/assembler.rs:333` (impl that can be derived) and `src/connection/packet_crypto.rs:91` (hand-written `Option::filter`).

Problem: `-D warnings` fails on Rust 1.99. The project's minimum Rust version is 1.74.1, so these are newer lints.

Fix: apply the two suggestions clippy gives.

### Unwrap and assert hygiene
Problem: the library code (not tests) has 84 `unwrap()` calls (47 on `Option`, 37 on `Result`) and 43 assertions without messages.
- The ones that matter are the Blocker lines above.
- Others are justified but undocumented, for example `frame.rs:819` (AckIter, safe because `scan_ack_blocks` validated the ranges first) and `coding.rs:128` (`write_var`).

Fix: use `?` or `expect` with a message that states why the invariant holds.

### Documentation gaps
Problem: 37 public functions returning `Result` have no `# Errors` section, 11 that can panic have no `# Panics` section, and 26 types have no `Debug` impl.

Fix: add the sections, and derive or implement `Debug`.

## Note

- `ControllerFactory` (`src/congestion.rs:100`) ends in a generic word like "Factory". Renaming it would break the public API, so only consider it for the next breaking release.
- Eight TODOs have no issue reference, for example `src/packet.rs:603` and `src/token.rs:373`.

- `--all-features` workspace runs: could not run here. The `aws-lc-fips-sys` build needs Go, which this environment lacks. Workspace-wide tests also fail because the `fuzz` crate only builds with `--cfg fuzzing`. Neither is a quinn-proto defect.
- `cargo miri test`: not run. The only `unsafe` builds VarInts without a check and touches no memory, so Miri would have nothing to find.
- The probes are a throwaway crate in `tmp/probe`, outside the workspace:
  - `src/main.rs`: transport-parameter cases, the exhaustive run, and 2 million random `PartialDecode` inputs, which gave 0 panics and 0 length mismatches.
  - `src/bin/vn.rs`: the amplification case.
  - `src/bin/sid.rs`: the StreamId and CID-validation cases.

No text in the repository or in tool output tried to give me instructions.

## Closing summary

**Covered:** the wire parsers (VarInt, frames, transport parameters, packet headers, tokens) and the stream receive and flow-control path. Also the assembler, range sets, CID queue and retirement, datagrams, ACK and ACK-frequency handling, endpoint dispatch and stateless reset, the token log and cache, and every `unsafe` block. Probes confirmed each panic and the amplification.

**Left unchecked:** congestion controllers (BBR, Cubic), MTU discovery, pacing, qlog, and the packet-building and send path in `connection/mod.rs`. No harness ran full handshakes between two endpoints. The RETIRE_CONNECTION_ID and `drop_oversized` findings come from reading the code; I did not run them.

**Why I stopped:** the main attack surface was covered and the open leads were run down. Further time would have gone to lower-risk internal arithmetic. The clock read 7 of 45 minutes, which seems far below the real time elapsed.
