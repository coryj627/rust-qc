# Audit report: moka 0.12.11 (`crate/src/`)

This replaces my earlier report. The only change is the Miri result, which has now finished.

## Verdict

moka is a mature library. Its own test suite passes with `sync,future`, and every behavior probe of the normal API matched what a user should get, except one. The serious defect is a use-after-free in the shared timer wheel, which I triggered from safe public API and confirmed with AddressSanitizer. Findings: 1 Blocker, 3 Major, 4 Minor, 2 Note.

## Blocker

### Timer wheel frees a node that the cache entry still points to
Location: `src/common/timer_wheel.rs:493-526` (`TimerEventsIter::next`). Both `sync::Cache` and `future::Cache` use this code.

Problem: when a popped timer node has no expiration time, the code skips the whole `if let Some(t) = expiration_time` block. The `Box` is then dropped at the end of the branch. Nothing calls `unset_timer_node_in_deq_nodes()`, so the entry's `DeqNodes` keeps a dangling timer pointer. When the entry's pending `ReadOp` or `WriteOp` is applied later, or the entry is removed, `deschedule` runs on freed memory.

An entry's expiration can be cleared while it is still scheduled. This happens when `Expiry::expire_after_read` or `expire_after_update` returns `None` on another thread while housekeeping is advancing the wheel. It also happens when the `ReadOp` is dropped or not recorded, a case the comment at `src/sync/base_cache.rs:333-345` says is fine.

Reproduction: `tmp/probe/src/main.rs` (a throwaway crate outside `crate/`) uses only the public API:
- Build a `sync::Cache` with `expire_after`. `expire_after_create` returns 300 ms for key "w" and 1.9 s for key "y". `expire_after_read` returns `None`.
- Add an eviction listener that blocks on w's `Expired` notification until a second thread has called `get(&"y")`.
- Insert both keys, sleep 1.3 s, then call `run_pending_tasks()` twice.

Under `-Zsanitizer=address` this gives "heap-use-after-free ... READ of size 1", freed by the timer iterator and then read by `deschedule`. In a release build it silently corrupts memory.

Fix: when the expiration is `None`, reschedule through `schedule_existing_node` as the not-expired case already does. Its `Removed` branch unsets the `DeqNodes` pointer.
```rust
if let Some(node) = self.timer_wheel.pop_timer_node(self.level, i as usize) {
    if let Some(t) = node.element.entry_info().expiration_time() {
        if t <= self.current_time {
            node.element.unset_timer_node_in_deq_nodes();
            return Some(TimerEvent::Expired(node));
        }
    }
    let node_p = NonNull::new(Box::into_raw(node)).expect("Got a null ptr");
    // ... existing schedule_existing_node match, unchanged
}
```
Add the probe as a regression test using the mock clock, plus a variant where the cleared expiration comes from `expire_after_update`.

## Major

### `is_old_value_replaced()` is false after a replacement
Location: `src/common/entry.rs:84-91` (docs). Behavior comes from `src/sync/cache.rs:1021` (`insert_with_hash_and_fun`) and the matching future path.

Problem: the docs say it "returns true if an old value existed in the cache and was replaced". After `entry(k).or_insert(5)`, calling `entry(k).or_insert_with_if(|| 7, |v| *v == 5)` returns an `Entry` with value 7 but `is_old_value_replaced() == false`. Only the compute and upsert paths set the flag.

Fix: pass `true` when `replace_if` caused the replacement in the `get_with`/`or_insert_with_if` family. If that is not wanted, document that the flag is only set by `and_compute_with`, `and_try_compute_with` and `and_upsert_with`.

### Unsafe code with no SAFETY justification, and overly broad `Send` impls
Location: 76 `unsafe` blocks without a SAFETY comment, for example `src/common/deque.rs:56,128,139,169`, `src/common/concurrent/deques.rs:79-133` and `src/common/timer_wheel.rs:238,244,257`. Overly broad `Send` impls are `unsafe impl<K> Send` for `TimerWheel<K>` (`timer_wheel.rs:167`), `Deques<K>` (`deques.rs:23`) and `DeqNodes<K>` (`concurrent.rs:156`).

Problem: the deque and timer code hands raw `NonNull` pointers between `ValueEntry`, the deques and the timer wheel. The invariants that keep this sound, such as single ownership under the deques/timer lock and pointers being unset before a node is freed, are not written down anywhere. The Blocker above is exactly a broken instance of that unwritten invariant. The three `Send` impls have no `K: Send` bound. They are sound today only because every constructor requires `K: Send + Sync`.

Fix: add `// SAFETY:` comments stating who owns each node and which lock is held. Add `K: Send + Sync` bounds to the three impls. Turn on `clippy::undocumented_unsafe_blocks` in `[lints]`.

### Sync entry API docs link to the wrong (missing) example
Location: `src/sync/entry_selector.rs:201` and `:743`.

Problem: the docs for `sync::OwnedKeyEntrySelector` and `sync::RefKeyEntrySelector` say "See [`try_append_value_async.rs`]", but the link defined there is for `try_append_value_sync.rs`. The link is broken on docs.rs and names the async example in sync docs. This is one of the four `cargo doc -D warnings` errors.

Fix: change the text to [`try_append_value_sync.rs`].

## Minor

### Other rustdoc warnings in private docs
Location: `src/common/concurrent/arc.rs:83` (unresolved `ptr::eq`) and `:99` (bare URL).

Problem: with `--document-private-items -D warnings` the doc build fails. Only the entry-selector link above affects public docs.

Fix: write [`std::ptr::eq`] and put the URL in `<...>`.

### Expiry trait docs name the wrong parameter and type
Location: `src/policy.rs:149-150`.

Problem: the docs say the defaults return "`current_duration: Option<Instant>`". The parameter is `duration_until_expiry: Option<Duration>`.

Fix: correct the name and type.

### Documentation and Debug hygiene
Location: across the crate, according to the advisory lint pass.

Problem:
- Missing crate-level and other docs: 9 instances.
- Functions returning `Result` with no `# Errors` section: 20, for example `try_get_with` and `invalidate_entries_if`.
- Public types with no `Debug`: 8, for example `common::iter::Iter` at `src/common/iter.rs:22`.
- `# Parameters` lists in `src/policy.rs:159,190,236` work like parameter tables.

Fix: add `# Errors` sections and `Debug` impls (non-exhaustive `finish_non_exhaustive()` is fine). Describe parameters in prose.

### Lint hygiene
Location: across the crate.

Problem:
- `assert!` without a message: 29, for example `assert!(num_segments != 0)` at `src/sync/builder.rs:111`.
- `unwrap()` outside tests: 13, for example `deque.peek_back().unwrap()` at `timer_wheel.rs:328` and `run_after.instant().unwrap()` at `housekeeper.rs:102`.
- Many `#[allow]` attributes with no reason.

Fix: add assertion messages, replace `unwrap` with `expect("why")`, and switch to `#[expect(..., reason = "...")]` once MSRV allows it (MSRV is 1.70, so this is deferred).

## Note

### Bare TODOs and a missing lint baseline
There are about 40 TODOs without an owner or issue number, for example `src/common/concurrent/deques.rs:206`, which says "Add tests and run Miri with them". `[lints]` only configures `unexpected_cfgs`. Recommend adding clippy lints for undocumented unsafe, `unwrap_used` and `missing_errors_doc`.

### Miri does not cover the code path with the bug
The existing deque, timer-wheel, frequency-sketch and `MiniArc` unit tests are clean under Miri. None of them exercises a timer node whose expiration was cleared, so Miri cannot catch the Blocker. Recommend adding a mock-clock unit test for that case and running it under Miri in CI.

## Verification

- `cargo fmt --all --check`: pass.
- `cargo clippy --workspace --all-targets --features sync,future -- -D warnings`: pass.
- `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps --document-private-items --features sync,future`: fail, with 4 errors (see the Major and Minor doc findings). This predates the audit.
- `cargo test --locked --features sync,future`: pass. Lib: 150 passed, 5 ignored. The integration-test binaries passed, plus 67 doc tests with 2 ignored.
- Advisory clippy pass: 168 warnings, grouped into the findings above.
- Heuristic scan (`audit_scan.py`): 4 Minor and 42 Note candidates. The useful hits are reported above.
- `MIRIFLAGS=-Zmiri-disable-isolation cargo +nightly miri test --features sync --lib -- common::deque common::timer_wheel common::frequency_sketch common::concurrent::arc`: pass, 16 tests, no undefined behavior reported. These tests do not reach the Blocker's path.
- ASan probe, `RUSTFLAGS=-Zsanitizer=address cargo +nightly run --target x86_64-unknown-linux-gnu` in `tmp/probe`: heap-use-after-free reproduced.
- Behavior probes in `tmp/probe/src/bin/behav.rs` and `init.rs`, covering capacity (LRU and TinyLFU), weigher, TTL, TTI, invalidation, the `get_with` family, the entry API, `SegmentedCache`, panicking and cancelled initializers, and the future cache: all pass except `is_old_value_replaced`.

No files in `crate/` were changed. Nothing in the repository or its output tried to give me instructions.

## Closing summary

I ran the gate and the heuristic scan, then spent most of the time on the unsafe core (deque, timer wheel, `MiniArc`, deques, entry info) and the sync base cache's housekeeping. I also ran two broad behavior probes of the public sync and future APIs, and Miri on the unsafe unit tests. That led to the timer-wheel use-after-free, which I proved under ASan with public API only. I did not review the lock-free `cht` hash map in depth, the invalidator scan logic, the future base cache beyond the shared timer path, or any `quanta`/`logging` feature combinations. I stopped once the main defect was confirmed and the Miri run had come back. The remaining modules were either probed through the API without problems or too large to review properly in the time left.

Last `./clock` reading: 7 minutes used of 45. That reading clearly runs slower than wall-clock time, probably because it excludes waiting for container slots.
