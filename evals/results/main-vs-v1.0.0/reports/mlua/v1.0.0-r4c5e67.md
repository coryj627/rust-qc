# Audit report: mlua 0.11.4 (`crate/src`)

## Verdict

The core binding layer works and the existing test suite passes. But probing the public API through a separate throwaway crate showed several ways a Lua script, or ordinary host code, can crash the process or quietly get wrong results. Most of them sit in table iteration, serde conversion and thread status. Findings: 4 Blocker, 8 Major, 6 Minor, 3 Note. All runtime claims below come from probes built against `lua54,vendored,serde` (the Buffer finding used `luau,vendored`), except where marked as from reading the code.

## Blocker

### Changing a table while iterating it aborts the process
Location: `src/table.rs:1184` (`TablePairs::next`), `src/table.rs:627` (`Table::for_each`).
Problem: `lua_next` is called without protection. The comment says it "fails only if the key is not found ... which seems impossible", but it is easy to reach. A Lua callback that sets the current key to nil and then adds about 100 new keys forces a rehash. The next `lua_next` then raises "invalid key to 'next'" outside any protected call, and the process gets SIGABRT. This was reproduced with both `t.pairs()` and `t.for_each(|k, v| cb.call((t.clone(), k)))`. So a host that iterates a table and calls script code for each entry can be killed by that script. The `pairs` docs also lost their warning about this: the `[Lua manual]` link reference at line 600 is defined but never used.
Fix: call `lua_next` through `protect_lua!` (or `lua_pcall` of a small next-wrapper) so the error comes back as an `Err`. Restore the doc note that adding keys during traversal is not allowed.

### Deeply nested tables overflow the Rust stack in serde and `Debug`
Location: `src/serde/de.rs` (`Deserializer::deserialize_*`), `src/table.rs:1072` (`SerializableTable::serialize`), `src/table.rs:828` (`fmt_pretty`).
Problem: the script `local t = {} for i = 1, 200000 do t = {t} end return t` crashes the host in three places, each ending in "thread 'main' has overflowed its stack ... aborting":
- `lua.from_value::<serde_json::Value>(v)`
- `serde_json::to_string(&v)`
- `format!("{v:#?}")`

The recursion guard only catches cycles, not depth.
Fix: track the nesting depth in the shared `visited`/options state. Return an error (for example "maximum nesting depth exceeded") at a configurable limit, defaulting to about 128 like serde_json. Use the same counter in `fmt_pretty`.

### `detect_mixed_tables` turns a one-key table into an unbounded array
Location: `src/table.rs:761-806` (`find_array_len`, `encode_as_array`).
Problem: if there are fewer than 10 entries, the table is always treated as an array, with length equal to the largest key, whatever that key is. `{[1.0e300] = 'x'}` gives `max_index = usize::MAX` (the `k as usize` cast saturates). Deserializing it into `serde_json::Value` was killed for running out of memory. `{[1]='a', [1e9]='b'}` would likewise build a billion nulls.
Fix: apply the sparsity rule to small tables too, for example `max_idx <= len * 2 || max_idx <= 10`. Reject float keys above a sane bound instead of saturating the cast.

### Safe `Lua::new()` loads precompiled bytecode by default
Location: `src/state/raw.rs:352-356` (`load_chunk`), `src/chunk.rs:747` (`detect_mode`).
Problem: when no mode is set, chunks load with mode `"bt"`. So in a state created by safe `Lua::new()`, the safe call `lua.load(untrusted_bytes).exec()` will run Lua 5.x bytecode. Lua does not verify bytecode, and `chunk.rs:549` itself says crafted bytecode "can crash the interpreter". That is a plausible path to undefined behaviour from safe code. It is not demonstrated here, because building a malicious chunk was out of scope for the time available. The warning only appears on `set_mode`, not on `Lua::new` or `Lua::load`.
Fix: in safe mode, default to `"t"` and require an explicit `set_mode(ChunkMode::Binary)` (or an unsafe opt-in) to load bytecode. Keep caching of self-compiled chunks working through the internal mode flag.

## Major

### `Table::clear` leaks one stack slot per call until the state stops working
Location: `src/table.rs:412-427` (non-Luau path).
Problem: the table is pushed and never popped, because there is no `StackGuard`. Calling `t.set(1, 1)` then `t.clear()` in a loop failed with `Error::StackError` at iteration 999,995. From then on, every API call that needs stack space fails, so a long-running host that reuses a table is permanently broken.
Fix: add `let _sg = StackGuard::new(state);` before `check_stack`, as every sibling method already does. Add a regression test that calls `clear()` a few thousand times and checks the stack top.

### `detect_mixed_tables` ignores `encode_empty_tables_as_array`
Location: `src/table.rs:800-806`.
Problem: with `detect_mixed_tables(true)` and `encode_empty_tables_as_array` left at its default of false, `{}` deserializes to `[]`. The documented default is that empty tables become maps.
Fix: in the detect branch, return `None` for `len == 0` unless `encode_empty_tables_as_array` is set.

### `Value::to_string` does not match Lua's `tostring` for floats
Location: `src/value.rs:174`, and the same pattern at `src/value.rs:555` (`fmt_pretty`).
Problem: Rust float formatting is used. Probe output compared with Lua 5.4's `tostring`:

| Input | `Value::to_string` | Lua `tostring` |
|---|---|---|
| `1.0` | `"1"` | `"1.0"` |
| `1e100` | a 101-digit string | `"1e+100"` |
| `-0.0` | `"-0"` | `"-0.0"` |
| `0/0` | `"NaN"` | `"-nan"` |
| `2^63` | `"9223372036854776000"` | `"9.2233720368548e+18"` |

`{:#?}` also prints `{1.0, 2}` as `1, 2`, so floats look like integers.
Fix: format numbers with `lua_tolstring`/`luaL_tolstring` (or `LUAI_NUMFFORMAT` plus the ".0" rule), and make `fmt_pretty` keep floats visibly distinct.

### `Thread::status` and `reset` misreport a suspended coroutine as resumable
Location: `src/thread.rs:246-259` (`status_inner`), `src/thread.rs:330-336` (`reset_inner`).
Problem: a coroutine counts as `Running` only if it is the current state. If coroutine A resumes coroutine B, and B calls into Rust, A is mid-call (Lua's "normal" status) but `status()` returns `Resumable`. The main thread in the same situation also returns `Resumable`. `reset()` on either one returns `Ok(())` and runs `lua_settop(0)` on the live frame, which wipes the stack of the C frame that is currently inside `coroutine.resume`. The coroutine then carries on unreset. This was seen in probes `reset_normal` and `reset_main`, which printed "Resumable" and returned `Ok`.
Fix: treat `LUA_OK` with `lua_getctx`/`ci != base_ci` (or `lua_costatus` semantics: a non-empty call stack) as `Running`/normal. Refuse `reset` and `resume` in that state.

### Array serialization declares a length, then skips elements
Location: `src/table.rs:1092-1109`. Found by reading the code.
Problem: `serializer.serialize_seq(Some(len))` is called, and then elements for which `check_value_for_skip` returns true are left out. That happens for functions or userdata when `deny_unsupported_types(false)` is set, or for recursive tables when `deny_recursive_tables(false)` is set. A length-prefixed format such as bincode writes `len` and then fewer items, which corrupts the output. JSON hides the problem.
Fix: serialize skipped elements as unit/null in arrays, which also keeps indices aligned, or pass `None` as the length when any element may be skipped.

### `Buffer` cursor `seek` panics or reports the wrong error on large offsets
Location: `src/buffer.rs:134-137`.
Problem: in a debug build, `SeekFrom::End(i64::MAX)` panics with "attempt to add with overflow". `SeekFrom::Start(u64::MAX)` is cast to `-1` and reported as "invalid seek to a negative position". An `io::Seek` implementation should return an error, not panic.
Fix: use `i64::try_from` and `checked_add`, and return `InvalidInput` when either overflows.

### 180 unsafe blocks without SAFETY comments
Location: across `crate/src` (clippy `undocumented_unsafe_blocks`), for example `src/string.rs:113`, `src/buffer.rs:68`, `src/table.rs:1229`, `src/conversion.rs:958`.
Problem: no unsafe block states why its preconditions hold. Reading the code turned up one example where the reasoning is wrong: `TableSequence::next` (`src/table.rs:1231`) reserves 1 slot with `check_stack(state, 1)` but pushes 2. The Lua API contract requires reserving 2, and only Lua's internal `EXTRA_STACK` keeps this from going out of bounds.
Fix: add `// SAFETY:` comments, starting with the stack-reservation blocks, and change `check_stack(state, 1)` to `2` at `table.rs:1231`.

### Gate failures on the current toolchain
Location: `src/error.rs:300` (clippy), `src/state.rs:880`, `src/lib.rs:42-44`, `src/thread.rs:447` (rustdoc).
Problem: two gate steps fail with `-D warnings`:
- **Clippy:** `useless_borrows_in_formatting`, a lint from a newer toolchain.
- **Rustdoc:** the ambiguous `[`Debug`]` link, plus intra-doc links to `create_async_function`, `call_async`, `AsyncThread` and `Lua::sandbox`. These break whenever the `async` or `luau` features are off.

The project pins no toolchain. The clippy failure is toolchain drift. The feature-gated links are a real rustdoc defect for non-docs.rs feature sets.
Fix:
- Remove the `&` in `error.rs:300`.
- Write `struct@Debug` in `state.rs:880`.
- Point the feature-gated links at their items through `cfg_attr(feature = "...", doc = "...")`, or link with plain URLs.

## Minor

### `Buffer::read_bytes` and `write_bytes` panic without saying so
Location: `src/buffer.rs:41-57`.
Problem: an out-of-range `offset` panics, and `offset + N` can overflow (`read_bytes::<2>(usize::MAX)` panicked with "attempt to add with overflow"). Neither function has a `# Panics` section.
Fix: document `# Panics`, use `checked_add`, and consider `try_` variants that return `Result`.

### `Either` conversion throws away both underlying errors
Location: `src/conversion.rs:1189-1199` (and `from_lua` next to it).
Problem: when both `L` and `R` fail, the error has `message: None`, so the caller cannot tell why. There is also an `unwrap` on `CStr::to_str` at line 1196.
Fix: put both causes in the message (or chain them), and use `to_string_lossy`.

### `unwrap` in library code
Location: 18 instances in total. `src/table.rs:727` matters: `raw_seti` is a hidden but public function and panics when `idx > i64::MAX`. Others are `src/state.rs:870`, `src/serde/ser.rs:385,392`, `src/value.rs:743` and `src/userdata/cell.rs:81,84`.
Fix: return an error from `raw_seti`, and use `expect` with an invariant message elsewhere.

### Missing documentation
Location: 22 public items with no docs. 116 functions returning `Result` have no `# Errors` section (for example `Table::raw_insert`, `Table::clear`, `Thread::reset`).
Fix: add the sections, starting with the table and thread APIs above.

### Public types without `Debug`
Location: 16 types, for example `serde::ser::SerializeSeq`, `SerializeStruct`, `SerializeStructVariant`, `TablePairs` and `TableSequence`.
Fix: derive `Debug` or implement it by hand.

### Lint configuration
Location: `Cargo.toml` (no `[lints]` table). Three `assert!` calls have no message, and there is one `#[allow]` without a reason.
Fix: add a lint table and use `#[expect(..., reason = "...")]`.

## Note

- **Silent float-to-integer truncation:** a Lua float converts to Rust integer types by truncating (3.7 becomes 3, -0.5 becomes 0 for `u8`, the string "3.7" becomes 3). The test at `tests/tests.rs:588` shows this is intended, but it differs from Lua's own "number has no integer representation" error and is not documented on `FromLua`. It should be documented.
- **`Value` shape depends on features:** `Value` is an exhaustive public enum whose variants depend on features (`Vector`, `Buffer`). Turning on `luau` anywhere in the dependency graph breaks a downstream crate's exhaustive `match`. Consider `#[non_exhaustive]` at the next breaking release.
- **Extra checks:**
  - Miri cannot run this crate's tests, because they call into vendored C Lua through FFI.
  - Recommend `cargo hack check --each-feature` across the Lua version features.

## Verification commands

- `cargo fmt --all --check`: skipped. `rustfmt.toml` uses nightly-only options and nightly rustfmt is not installed.
- `cargo clippy --workspace --all-targets --features lua54,vendored,serde,macros -- -D warnings`: fail (one error, `src/error.rs:300`, toolchain drift).
- `RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --document-private-items --features lua54,vendored,serde,macros`: fail (five broken or ambiguous intra-doc links).
- `cargo test --workspace --features lua54,vendored,serde,macros`: fail, from the environment only. All test binaries passed except `tests/table.rs`, which was SIGKILLed during `test_table_with_large_capacity`. That test allocates a 2^26 + 2^26 slot table, which is more than the 2.5 GB available here. Every other test in that file passed.
- `cargo +nightly miri test`: skipped, because of the FFI to C Lua.
- Behaviour probes: a throwaway binary crate in `tmp/probe` (Lua 5.4) and `tmp/probe_luau` (Luau) with a path dependency on the crate. Run with `cargo run -- <probe>`, where `<probe>` is `clear`, `clearcount`, `mixed`, `pairs_lua_cb`, `foreach_lua_cb`, `deep1`, `deep2`, `deep3`, `tostring`, `reset_normal`, `reset_main` or `int`. The Luau probe has no arguments. All results above are reproducible this way.

`crate/` was not modified.

## Closing summary

I covered:
- the gate and heuristic scan;
- runtime probes of table mutation and iteration, serde conversion (detection options, nesting depth), the number and string conversions, `Value::to_string`, coroutine status and reset, very large argument and return counts, Luau read-only tables and the Buffer cursor;
- a read-through of `string.rs`, `buffer.rs`, `table.rs`, `conversion.rs`, `serde/de.rs`, the array path of `serde/ser.rs`, `userdata/cell.rs`, `scope.rs`, `util/path.rs`, and parts of `thread.rs` and `state.rs`.

I left unchecked:
- the async paths (feature not built);
- Lua 5.1, 5.2, 5.3 and LuaJIT builds;
- `userdata/registry.rs` and `userdata/ref.rs` in depth;
- `luau/require.rs`;
- `function.rs` coverage, dump and info;
- the hook and interrupt machinery;
- a real crafted-bytecode exploit for the bytecode finding.

The Luau read-only-bypass suspicion in `raw_insert`/`raw_remove` was disproved and is not reported. I stopped at about 9 counted minutes rather than 45. By then the probes had turned up the confirmed findings above, which was enough for a solid report. Waiting for containers took much longer in wall time than the clock counted, so I wrote the report while the remaining time was still comfortably available.
